# Velaqua Water Intelligence Platform

**AI-powered predictive leak detection and incident decision intelligence for water distribution networks.**

Repository: [github.com/DougMoore123/Velaqua-Water-intelligence-Platform](https://github.com/DougMoore123/Velaqua-Water-intelligence-Platform)

## Executive Summary

Velaqua converts pressure, flow, demand, and operational telemetry into real-time leak-risk predictions, evidence-backed incident recommendations, and governed field actions. The reference implementation is built for Microsoft Azure with Azure ML, Databricks, ADLS Gen2, FastAPI, Azure AI Search, Azure OpenAI, GitHub Actions, and Azure Monitor.

The system is designed around five operating principles:

- **Operational value:** prioritize missed-leak reduction, early detection, and business impact rather than model scores alone.
- **Traceability:** link source telemetry, features, predictions, decisions, RAG evidence, and approvals with `incident_id` and `asset_id`.
- **Controlled autonomy:** material field actions require an explicit human approval record.
- **Release discipline:** model and service changes move through quality gates, blue/green validation, smoke tests, and rollback capability.
- **Evidence over invention:** RAG responses are grounded in retrieved documents, cite their sources, and fall back deterministically when dependencies fail.

### Capability layers

1. **Data acquisition:** ADF batch ingestion and Event Hub streaming.
2. **Data engineering:** Databricks/PySpark bronze-silver-gold processing, schema enforcement, and data-quality checks.
3. **ML development:** feature engineering, model-suite training, calibration, threshold sensitivity, stress testing, and lineage.
4. **Model governance:** production candidate selection, performance gate, data sufficiency gate, model registration, and approval records.
5. **Serving:** AML CLI v1 realtime and batch deployments with blue/green release controls.
6. **Decision intelligence:** FastAPI endpoints for prediction, incident orchestration, approvals, readiness, and executive KPIs.
7. **Evidence synthesis:** Azure AI Search retrieval and Azure OpenAI generation with citations, context limits, blocklists, and deterministic fallback.
8. **Operations:** dashboards and integration contracts for CMMS, field workflows, customer service, and executive reporting.
9. **Governance:** CI/CD, observability, security baselines, cost controls, ownership, retraining triggers, and rollback procedures.

## Decision API

| Endpoint | Purpose |
|---|---|
| `GET /health` | Liveness probe |
| `GET /ready` | Readiness and RAG configuration visibility |
| `POST /predict` | Risk tier, confidence, decision context, and approval requirement |
| `POST /incident` | Authorization-gated incident orchestration and integration fanout |
| `POST /incident/approval` | Operator approval or rejection for material actions |
| `GET /kpi/executive` | Aggregate incident KPI summary |

Important runtime settings include `RAG_SERVICE_URL`, `RAG_TIMEOUT_SECONDS`, `RAG_MAX_RETRIES`, `RATE_LIMIT_WINDOW_SECONDS`, `RATE_LIMIT_MAX_REQUESTS`, `GENAI_BLOCKLIST_TERMS`, `RAG_MAX_CONTEXT_CHARS`, and `RAG_MIN_RETRIEVED_DOCS`. Integration targets are configured through the `OPS_DASHBOARD_URL`, `CMMS_WORK_ORDER_URL`, `FIELD_WORKFLOW_URL`, `CUSTOMER_SERVICE_WORKFLOW_URL`, and `EXECUTIVE_KPI_URL` variables.

## RAG and Evidence Synthesis

The RAG service uses Azure AI Search for retrieval and Azure OpenAI for generation. The seed corpus includes SOPs, equipment manuals, and incident history.

```bash
./scripts/configure_rag_services.sh
python scripts/index_rag_corpus.py
python scripts/evaluate_rag_quality.py
```

Quality outputs include `grounded_rate`, `citation_rate`, `hallucination_rate`, and per-case `source_recall`. The service supports API-key and Managed Identity / Entra authentication. Retrieval or generation failures return deterministic fallback evidence rather than blocking decision processing.

## CI/CD and Governance

The CI workflow runs lint, unit, API, schema, data-quality, model-governance, deployment, and orchestrator tests. The CD workflow enforces quality gates, model checks, blue/green validation, rollback validation, a protected production approval environment, and green promotion.

Production promotion requires all of the following:

- Model performance and data sufficiency gate passes.
- Smoke, load, timeout, and blue/green checks pass.
- Human approval record is complete and valid.
- Security, monitoring, and cost baselines are configured.
- Rollback procedure has been validated.

Do not commit runtime secrets, raw datasets, local Azure configuration, model artifacts, or monitoring logs. See [.gitignore](.gitignore) and [.env.example](.env.example).

## Release Position

The repository is engineering-ready for controlled integration testing: code quality, automated tests, service contracts, deployment automation, observability logic, and governance controls are implemented. It is **not yet approved for unrestricted production promotion** because the current model evidence is based on insufficient real data, synthetic monitoring produces data-quality warnings, and the human approval artifact is intentionally incomplete.

That distinction is deliberate: the platform reports strong infrastructure and runtime behavior while refusing to claim production model readiness without representative operational evidence.
